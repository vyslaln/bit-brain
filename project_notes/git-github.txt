git config
Git ayrı bir programdır; komutları Git Bash'te, PowerShell'de ya da
VS Code terminalinde çalışır. git config, Git'in nasıl çalışacağını
belirleyen ayarları görmemi, eklememi ve değiştirmemi sağlayan komuttur.

Ayarlar üç seviyede tutulur:
- --system : bilgisayardaki tüm kullanıcılar için
- --global : benim kullanıcı hesabımdaki TÜM projeler için
             (ana dizinimdeki .gitconfig dosyasına yazılır)
- --local  : sadece içinde bulunduğum proje için
             (projedeki .git/config dosyasına yazılır)
             Seviye yazmazsam varsayılan budur; proje klasöründe
             değilsem hata verir.
--global, --local gibi ifadeler komut değil, komutun seçenekleridir.

user.name ve user.email, attığım her commit'e "bunu kim yaptı"
bilgisi olarak eklenir.

Küçük örnek:
git config --global user.name "Veysel ..."    -> ad ayarlar
git config --global user.email "..."          -> e-posta ayarlar
git config --global user.name                 -> ayarlı adı gösterir
git config --global --list                    -> tüm global ayarları listeler

Dikkat / tuzak:
- user.name ve user.email bir İMZA değildir, sadece etikettir. Git
  doğrulamaz; herkes istediği adı yazabilir. Gerçek imza ayrı bir
  konudur (commit signing).
- Commit'teki e-posta, repo public olunca herkese görünür. Gizlemek
  için GitHub'ın noreply adresi kullanılabilir.
- Seçenekler iki tireyle yazılır: --global, --list. Tek tire yanlış.

pwd nedir?
Print working directory/mevcut dizini yazdır anlamına gelir. Çalışmakta olduğum mevcut dizini görmemi sağlar. 

Örnek:
$ pwd  --komut 
/c/Users/Veysel/OneDrive/Desktop/bit-beyin --çıktı

Şu anda masaüstümde bulunan bit-beyin klasörü içerisindeyim (proje klasörüm)

init.defaultBranch nedir?
Default branch, git init komutuyla yeni bir repo oluşturulduğunda atanan default olarak tanımlanmış (yani repo oluşturulur oluşturulmaz atanan = default umarım net ifade edebilmişimdir kendimi) branch'i ifade eder. 
Git hâlâ varsayılan olarak master verir; ben init.defaultBranch ayarıyla main yaptım.
Git kendi varsayılanını değiştirmedi, sadece init.defaultBranch ayarını ekledi.
master/slave (efendi/köle) çağrışımı.


Örnek:
git config --global init.defaultBranch main --komutumuz

çıktı olarak şu an bir şey dönmedi. Git için sessizlik = başarı. 

branch (dal) nedir?
Branch, ana kodu bozmadan yeni özellikler eklemek veya hataları gidermek için projenin birbirinden bağımsız kopyalarını oluşturan izole çalışma alanlarıdır.

İzole alan: yapılan değişiklikler sadece çalışılan dalda kalır.
Ana kodun güvenliği: main-master her zaman temiz ve çalışır durumda kalır.
Paralel çalışma: aynı proje üzerinde birden fazla yazılımcı birbirini engellemeden çalışabilir.

git init nedir, ne işe yarar?
normal bir klasörü boş bir git reposuna döndürmemizi sağlar.
.git klasörü = deponun kendisi (commit'ler, branch'ler, proje ayarları), "hafıza"
Adı nokta ile başlar → gizli, kazara dokunulmasın diye
Silinirse: dosyalar kalır, geçmiş gider; push'lanmışsa GitHub'da son push'a kadar durur 
Dikkat: git init'ten önce pwd; ana dizinde yazarsan tüm kullanıcı klasörün depo olur

ls nedir? 
ls, git'in temel olarak gelen komutlarından değil, Linux üzerinden gelen bir komuttur. Bu komut linuxta bir klasörün içerisindeki alt dizinleri ve dosyaları listememizi sağlar. Ama git projelerinde ve terminal üzerinden de klasörün  içerisindeki alt klasör ve dosyaları listelemek için kullanılır. Çok sık kullanılan 3 farklı parametresi vardır:

ls -a :Normalde gizli olan (.) ile başlayan dosyalarıda listeler.
ls -l: Dosyaları boyut, değiştirilme tarihi ve izinler gibi uzun bir listeyle gösterir.
ls -la: Hem gizli dosyaları hemde ayrıntılı dosyaları gösterir.

git status nedir?
Çalışma dizininin ve git reposunun o anki durumunu gösteren 'en temel' git komutlarından biridir. 
=== git status satırları ===
No commits yet;
  Henüz commit yok. 
  Projeyi açmışız, belki içinde dosya var ama commitini atmamışız.
  -- Burada yapılacak olan şey : git add dosya_adi + git commit (ilk commit)

nothing to commit;
  Projede commit atılacak bir değişiklik olmadığını gösteriyor.
  -- Burada yapılacak olan şey : hiçbir şey. Çünkü değişiklik yok.
  ** Ayrıca burada ben gidip git add yaparsam, bana hiçbir geri dönüşü olmaz. Yani bu da sessizce hiçbir şey yapmaz.***

Untracked files;
  Git'in gördüğü ama daha git add yapılmamış olan dosyaları belirtir.
  -- .gitignore içerisindeki dosyalar burada görünmez, Git onları yok sayar.
  -- Burada yapılacak olan şey : git add dosya_adi + git commit 

Changes to be committed;
  Daha commitlenmemiş, commitlenecek değişiklikler.
  -- Burada yapılacak olan şey : git commit 


Changes not staged for commit;
  Dosyada değişiklik yapıldı ama git add yapılmadı.
  -- Burada yapılacak olan şey : git add dosya_adi + git commit 

Your branch is up to date with 'origin/main';
  main ile origin/main aynı commitlere sahip.
  origin : Github'daki reponun takma adı.
  main : bilgisayarımdaki dalın adı.
  origin/main : Github'taki mainin bilinen son hali.
  -- Git bunu, Github'a bakmadan en son bildiği hale göre söyler.
  -- Burada yapılacak olan şey : hiçbir şey.

working tree clean;
  Çalışma alanı temiz. Son commit'ten bu yana commitlenmemiş bir değişiklik yok.
  -- Burada yapılacak olan şey : hiçbir şey

Your branch is ahead of 'origin/main' by 1 commit;
  Benim main dalım, origin/main'den 1 commit önde.
  Yani bende olup Github'da olmayan 1 commit var.
  --- 
    Tersi : behind = geride.
    Github'da olup bende olmayan bir commit.
  ---
  -- Burada yapılacak olan şey : git push

nothing added to commit but untracked files present;
  Commit'e hiçbir şey eklenmedi ama takip edilmeyen dosyalar var.
  (nothing to commit'ten farkı klasör boş değil, sadece staging area boş.)
  -- Burada yapılacak olan şey : git add dosya_adi + git commit

Git güncellemesi .git klasörünü ve commitleri etkiler mi?

Tahminim (Araştırmadan ÖNCE):
Etkiler; yeni özellik gelirse Git commitleri, klasörleri ve .git'i bu güncellemeye göre düzenler.

Araştırmadan SONRA:
Güncelleme proje içerisindeki .git klasörünü ve commitleri etkilemez.

Üç temel sebebi var:

1- Veri ve Program Ayrımı:
Bunun sebebi Git'in bir program, .git'in ise; Git programının okuduğu bir veri olması.
Örnekle izah edersek bu durumu eğer;
Word güncellenince, word dosyalarının içeriğinin  değişmediği gibi Git güncellenince de .git değişmez.

Güncellemeyle gelen yeni Git sürümü, eski sürümlerle oluşturulmuş repoları okuyabileceği şekilde tasarlanır.

3- Commitlerin Değişmezliği:
Commit yazıldıktan sonra değiştirilemez çünkü 'hash' dediğimiz bir kodu vardır.
Bu 'hash' kodunu, kendi TC Kimlik Numaramız nasıl varsa projeye yazılan commitlerinde 'hash' adında bir kimlik kodu vardır. 
Commit'in 'hash' kodu da, commit'in içeriğinden hesaplanır. 
Eğer içerik değişmiş olsaydı, 'hash' kodu da değişirdi.

.gitkeep nedir? Boş bir klasörü Git'e nasıl ekleriz?
Git boş klasörleri takip etmez. 
Boş bir klasörü takibe almak için içine küçük bir dosya konur;
yaygın adı .gitkeep'tir.

Resmi git dökümantasyonunda (git-scm.com), .gitkeep adında bir anlatı yok.
Bu da bunun Git'in özel bir dosyası değil yazılımcılar tarafından geliştirilmiş
bir gelenek olduğunu doğruluyor:

Bu geleneğin iki sebebi var : 

1- Anlamlılık : 
Bu projeyi inceleyen bir yazılımcı klasörün içinde bu dosyayı gördüğünde, projeyi geliştiren
kişinin bu dosyayı boş klasörün Git tarafından takip edilebilmesi için eklediğini anlar.
Dosyanın adını farklı bir şey de koyabilirim (hello-world.txt, .bos-klasor gibi)  ama yazılımcı topluluklarında kabul gören 
adı .gitkeep'tir.

2- Düzen : 
Dosyanın adı (.) ile başladığı için işletim sistemlerinde varsayılan olarak gizli olur.
Bu da kod yazarkene gözümüzü yormaz.

***Alternatif Yöntem Olarak ; 
Bazı yazılımcılar yeni klasörün içine bir .gitignore dosyası açar ve bu dosyanın 
sadece klasörü takibe almak amacıyla eklendiğini comment yoluyla anlatır.

--Küçük Örnek : 
touch guides_notes/.gitkeep

**Dikkat/Tuzak : 
--- Git boş klasörü silmez; sadece görmez, bu yüzden commit'e ve Github'a gitmez.
--- .gitkeep bir kural değil, yazılımcı topluluklarında kabul gören bir gelenektir.
Git onu özel bir dosya olarak tanımaz.

Conventional Commits (commit mesajı standardı)
Commit mesajının ana yapısı : 

<type>[optional scope]: <description>

[optional body]

[optional footer(s)]

< > : zorunlu. Her commit'te type ve description olmak zorunda

[ ] : isteğe bağlı (optional). Gerektiğinde eklenir
Bu gösterim dökümantasyonlarda komut anlatırken de kullanılır.

- type : commit'in türü (öneki). Örn : docs

- scope : değişikliğin projenin hangi bölümünü etkilediği, parantez içinde. Örn : feat(theme): add dark mode toggle

- description : ne yaptığımı anlatan kısa cümle. İngilizce emir kipinde küçük harfle başlar, sonda nokta yok

- body : ayrıntılı açıklama. bu projede Türkçe kısım

- footer : BREAKING CHANGE (geriye dönük uyumsuz değişiklik) ya da Closes #3 gibi issue bağlantısı


Önekler : 

feat : Uygulamaya yeni bir özellik eklendiğinde. Örn : feat: add AI chat bot page

fix : Hata bulunduğunda ve çözüldüğünde. Örn : fix: correct node_modules name in .gitignore

docs : Belge eklendiğinde veya güncellendiğinde, dosya türü önemsiz. Örn : docs: add learning notes for Git and terminal

style : Kodun anlamını değiştirmeyen biçim değişiklikleri (CSS DEĞİLLLL). Örn : style: format input.css

refactor : Kodu yeniden düzenleme; davranış değişmez, yeni özellik ya da hata düzeltmesi yok. Örn : refactor: rename variables to English

chore : Projenin işleyişi, ayarı, bakımı. Örn: chore: add .gitignore for node_modules and .env

*** Önek dosya türüne göre değil, değişikliğin ANLAMINA göre seçilir.***

Tahminlerim : 

Araştırmadan önce : 
- Yapı : önek + başlık + "yazılacak olan commit"

- docs : md dosyası, chore : yeni dosya/klasör, style : CSS

*** Dikkat / Tuzak : 
-- 3 kez dosya türüne göre tanımladım. Örneklerim kendi tanımımla çelişiyordu. (notlar .txt'ydi ama docs aldı)

-- style'ı adından tahmin ettim, araştırmadım, tuzağa düştüm. Araştırmayı atladığım tek örnekti onda da yanılmış oldum.

-- Boş klasör açmak 'docs' değil, chore (guides_notes)

-- Gerçek bir CSS değişikliği : 
  feat :  yeni tasarım
  fix : eski bozuk tasarımı düzeltme
  sadece biçimlendirme : style

-- Şablonu ilk iki denemede kopyaladım; kendi cümlelerimle anlatınca anladım.

-- Commit mesajında; iki nokta üst üsteden önce boşluk olmaz : 
  style : (yanlış kullanım) style: (doğru kullanım) ***

mv ve git mv (dosya adını değiştirmek / taşımak)

mv : 
-- İşletim sistemi komutudur.

-- Dosyayı taşır ya da adını değiştirir, ama değişiklikten Git'in haberi olmaz. 

-- Git eski dosyanın tamamen silindiğini ve yerine yeni dosyanın eklendiğini düşünür.

-- git status -> eski ad "deleted", yeni ad "untracked"

git mv:
-- Git'in kendi komutudur.

-- Dosyanın adını ya da yerini hem bilgisayarda hem de Git'te değiştirir.

-- Değişikliği hemen staging area'ya ekler.

-- Yani git mv = mv + git add 

-- git status -> "renamed: eski -> yeni"


Küçük örnek : 
git mv project_notes/git-bash.txt project_notes/git-github.txt

*** Dikkat / Tuzak : 
-- git mv'den sonra git add yazmaya gerek yok; değişiklik zaten staging area içerisinde

-- git status çıktısındaki parantez içi satırlar "ne olduğunu değil", "ne yapabileceğimi" söyler. 
  Örn : "git restore --staged" : 
  Değişikliği staging area'dan çıkarmanın yolu. 

-- Dosya adı değişikliğinde 'update' değil, 'rename' kullan. ***

=== 04.10 - 15.10 EKLERİ ===

BRANCH AKIŞI (kendi cümlemle)
  Branch'i açarım, içini doldururum (commit). Editörde git merge ile de
  birleştirebilirim, ama GitHub üzerinden: push -> Pull Request ->
  açıklama -> Merge -> branch'i hem GitHub'dan hem editörden silerim.

  git switch -c feature/hero        -> branch aç ve ona geç (c = create)
  ... çalış, commit'le ...
  git push -u origin feature/hero   -> branch'i İLK KEZ gönder (-u = eşleştir)
  GitHub: Pull Request -> açıklama -> Merge -> Delete branch
  git switch main                   -> main'e dön
  git pull                          -> GitHub'daki yeni main'i indir
  git branch -d feature/hero        -> yereldeki branch'i sil
  git fetch --prune                 -> GitHub'da silinen branch izlerini temizle

  git branch       -> branch'leri listeler, * = şu an bulunduğum
  İsimler: feature/... (yeni şey), fix/... (hata düzeltme)
  Tuzak: Üzerinde durduğum branch'i silemem, önce başka branch'e geç.
  Tuzak: git branch -c = KOPYALAMA, branch açmak değil.

PULL REQUEST
  - main'e "şu branch'teki değişiklikleri al" isteği.
  - Başlık İngilizce, açıklama Türkçe; Markdown desteklenir:
      ### başlık     - madde     `kod`
    Yazdıktan sonra Preview sekmesinden kontrol et.
  - Merge sonrası log'da "Merge pull request #N" commit'i oluşur.
  - Issue ve PR numaraları aynı sayaçtan gelir (#4 = 3 issue + 1 PR).

COMMIT DÜZELTME VE SAHNE
  git commit --amend -m "..."  -> SON commit'i düzeltir.
      SADECE push'tan ÖNCE. Yeni commit oluşturur (hash değişir).
      Tuzak: Sahnede (staged) ne varsa onu da commit'e katar.
  git restore --staged dosya   -> dosyayı sahneden indirir (silmez).
  git status -u                -> klasörleri açıp her dosyayı tek tek gösterir.
  git log -2                   -> son 2 commit'in başlığı + gövdesi (q ile çık).
  git mv     -> TAKİP EDİLEN dosyayı taşır. Takipsiz dosyada çalışmaz.
  mv         -> takipsiz dosya için yeterli.

ÖNEKLER (Conventional Commits)
  feat     -> kullanıcı yeni bir şey görür
  fix      -> bozuk bir şey onarılır (hata bulunur, çözülür)
  refactor -> davranış AYNI, kodun içi/düzeni değişir
  chore    -> kurulum, ayar (.gitignore, npm install)
  docs     -> not, günlük, README
  style    -> kod BİÇİMİ (boşluk, girinti). CSS DEĞİL!
  Kural: Başlık İngilizce + emir kipi (add, fix, split),
         gövde Türkçe, o commit'te NE değiştiğini anlatır (geçmişi değil).

YOLLAR VE UYARILAR
  - Git komutlarını REPO KÖKÜNDEN çalıştır (önce pwd).
    project_notes içindeyken "project_notes/x.txt" -> project_notes/project_notes/x.txt arar.
  - LF / CRLF uyarısı hata değil: Windows satır sonu dönüşümü (core.autocrlf).
  - .gitignore zaten takip edilen dosyayı durdurmaz -> git rm -r --cached ([ARAŞTIR]).
  - touch dosya.txt -> boş dosya oluşturur.
